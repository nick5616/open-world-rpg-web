# 0014: Loot, rarities, forging and drops (WP14)

Status: accepted (WP14). Contract changes: `docs/cr/010-loot.md`.

## Context

Spec 8 asks for eight rarity tiers with fixed odds, personal loot, affixes,
sockets, gem cuts, ores, smelting, blueprints, forging at town forges,
consumables and cooking, dropping items as world pickups for 10 minutes,
`tradeable` and `provenance` on every item, and one transfer path
(`TransferItem`). Spec 11 adds the hard rule: "Loot grants are a single
transaction ... A crash can lose a roll but never duplicate one", while
"zone servers never block a tick on Postgres" and zone memory is
authoritative. WP16 (handoff, merged during WP14) adds an ownership epoch
per character so a stale zone's writes never land over the new owner's.

## Decisions

1. **One item table for both sides.** `contracts/items.yaml` →
   `npm run gen` → `server/pkg/itemdefs` (embedded JSON) and
   `@lodestone/contracts` `ITEMS`. Item keys (`ore:iron`, `gem:ruby:cut`,
   `weapon:sunsteel_blade`) are the contract other packages use (WP09
   drops, WP20 shops, WP15 sunsteel rule). Families (gems × cuts, ores,
   ingots, blueprints) are expanded by the generator, which also refuses a
   recipe naming an unknown item or a weapon type combat.yaml lacks.

2. **Odds and luck.** The base odds are spec 8's numbers exactly; luck
   (item level is implicit in the base choice, source: elite ×2, boss ×4,
   deep cave ×2, chest ×1.5, Opal/lootFind +1 % per point) multiplies the
   rare-and-above tiers, capped at 60 % of rolls in total; common absorbs
   the rest. Bitchin' is never shifted (fixed 1e-6, "anywhere"). A
   Primordial roll moves the item onto its starmetal (voidglass for deep
   sources) counterpart. Random loot never rolls sunsteel: sunsteel comes
   from sunsteel ore at a forge, so WP15's "only sunsteel kills demons"
   stays tied to mining daylight veins.

3. **Personal loot as owner-only pickups, containers straight to the
   bag.** Kill and vein loot pop out as WP09 pickup entities only their
   owner sees and auto-takes on touch; each pickup is its own grant (key
   `kill:<boot>:<enemy>:<tick>:<i>`, `vein:<seed>`). A container's roll
   goes into the inventory in one transaction with its
   `container:<id>` marker (overflow spills as personal pickups). The
   container seed is `(world seed, container id, character)`, so a roll
   lost to a crash rolls the same items again.

4. **The item journal, not the write-behind queue.** Item changes must
   reach Postgres in order and never be coalesced or skipped. Every change
   is one `ItemOp` (one transaction) on an ordered per-zone journal with one
   worker; the head op is retried until it commits; every op writes
   absolute row state (idempotent on a lost COMMIT reply); ops that create
   items from a roll or take one from the world insert a `loot_grants`
   marker first (a conflict with another op id = already granted, nothing
   inserted; with our own op id = our retried commit, success). Memory is
   updated at once (optimistic), so the database is always a prefix of the
   zone's history: a crash loses a suffix, never duplicates. An op that can
   never commit (a genuine duplicate grant, a row in the wrong state)
   quarantines the character: their remaining ops are dropped and they are
   kicked, so memory reloads from the database.

5. **`loot_grants` instead of the `containers_opened` bitset.** Container
   ids are 64-bit stable generator ids, not dense indices; a table keyed by
   (character, grant key) is the per-character "opened" record, the boss
   weekly lockout (`boss:<group>:<ISO week>`) and the exactly-once marker
   in one.

6. **WP16 epoch fence.** Item ops carry the zone's ownership epoch;
   `item_epochs` refuses an op older than the newest writer. The inventory
   crosses a handoff live in the handoff state (a `HandoffField`), and the
   new owner's first op is a full sync (all rows it holds, the rest of the
   character's rows deleted, all markers) at its newer epoch. Old-owner ops
   that land before the sync are overwritten by it; those after are fenced.

7. **Stacks merge; provenance merges too.** Plain stacks (no affixes,
   sockets, name, rarity) of the same base and trading flags merge; the
   receiving stack's provenance absorbs the incoming entries (bounded to the
   newest 32). Rolled items never stack.

8. **TransferItem.** One function moves items character → world (drop),
   world → character (take), character → character (trades later; no
   Interact exposes it in v1). Every move appends provenance. A drop by a
   local profile marks the item unverified and untradeable. For local
   profiles the signed blob without the item is issued before the world row
   exists (the drop is parked until the next local-save issue, which shares
   the write-behind key so a stale issue can never run after it); a local
   take adds the item only after the world row's delete committed. Lose,
   never duplicate, on both sides.

9. **Stations.** Forges and anvils use WP20's `Config.Stations` hook: the
   hook records the open station and returns false so WP20's Event 805
   still opens the UI; crafting (Interact 22) must happen within 7 m of the
   open station. Cooking opens at inn hearths and campfires (props 4, 22).
   Smelting and forging both happen at a forge or anvil.

10. **Gold.** The spec prices nothing in a currency, but WP20's shops and
    bounties carry prices. `currency:gold` is a purse stack (no slot); WP20
    purchases now cost gold (CR 010). Characters start with 20 gold and 3
    healing draughts (the starter grant, exactly once).

11. **Consumables replace the stand-in draught.** combat's `Player.OnDrink`
    spends the chosen (else the strongest) consumable from the inventory
    when a drink starts; the heal is the item's; charges no longer refill
    on respawn. Without the hook (WP13 simulations) the old behaviour stays.

12. **Gear into combat.** `combat.Gear` on the player: weapon multiplier
    (material × level), damage/crit/spell power/armor/health from affixes
    and uniques, socketed gem cut for forms, and WP15's `KillsDemons` /
    `Stagger` flags. The loadout's weapon type and gem element follow the
    equipped item; choosing a training weapon through WP13's combat
    Interact unequips the item.

## Consequences

- `npm run migrate` must run after merge (migration 0014).
- A zone with no database keeps items in memory only (bots, dev tickets);
  a character whose items fail to load plays with a memory-only inventory
  that is never saved over the real one.
- Item handles on the wire are zone-local u32s; they change on reconnect.
